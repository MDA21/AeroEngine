# AeroEngine — AI-Native 引擎设计方针

> 2026-05-31 讨论总结。基于对 Unity SRP、Unreal FSceneRenderer 架构分析，以及对 LLM 能力边界的评估，
> 形成 AeroEngine 的 AI-Native 演进路线和核心设计决策。

---

## 1. 核心判断

### 1.1 "AI Friendly" vs "AI Native"

| | AI-Friendly (MCP / Tool Call) | AI-Native |
|---|---|---|
| AI 能做什么 | 调用预定义函数 | 理解场景、表达意图、参与创作 |
| 状态安全 | 靠 prompt 约束 | 引擎侧约束系统保证 |
| 失败恢复 | 基本没有 | 操作前检验 + 回滚 |
| 上下文效率 | 原始数据（数千 tokens） | 语义摘要（数百 tokens） |
| AI 的角色 | 遥控器 | 合作者 |

**核心命题：AI 接入引擎的真正难点不是"让 AI 调用函数"，而是让 AI 知道调用哪个函数、
在什么状态下调用、调用后会有什么后果。**

### 1.2 LLM 的边界

```
LLM 擅长的：                       LLM 不擅长的：
✅ 意图理解（"把场景变暗"）         ❌ 精确状态追踪（"binding 2 的地址"）
✅ 高层规划（"先调整光再改材质"）    ❌ 数值分析（"5000 帧 GPU 时间序列"）
✅ 多模态感知（理解截图内容）        ❌ 程序分析（"shader compute occupancy"）
✅ 自然语言到结构化输出             ❌ 确定性逻辑（"这个操作安全吗"）
```

**结论：真正的 AI-Native 不是一个 LLM 控制一切，而是一组小而专的 AI 组件，各司其职。**

### 1.3 性能边界

```
一个帧：             16.67ms (60fps)
LLM 推理：           100ms – 2000ms  (慢 6-120 倍)
本地小模型 (7B)：     50ms – 200ms   (慢 3-12 倍)
ONNX 推理 (极简)：    2ms – 10ms     (可嵌入帧循环)
传统算法 (规则/统计)： <0.1ms         (零影响)
```

**结论：LLM 永远不能和渲染在同一时间轴上运行。AI 线程产出"编辑计划"，
渲染线程在下一帧应用计划——两者完全异步。**

## 2. 架构演进路线

### 2.1 概况

```
阶段 0  ✅  阶段 1  🔄  阶段 2   ⬜  阶段 3-4  ⬜  阶段 5-7  ⬜
基线      渲染引擎      工具化        AI 接入        AI-Native
```

### 2.2 各阶段架构形态

```
═══════════════════════════════════════════════════════════════

阶段 1 (当前) — 渲染引擎基线
───────────────────────────────────────────────────────────────
AeroEngine → SceneRenderer → VulkanDevice
              AssetManager ↗

目标：完整的、可发布的 Vulkan 渲染引擎
关键交付物：CPU/GPU-Driven 对比、大型场景演示、技术总结

═══════════════════════════════════════════════════════════════

阶段 2 — 引擎工具化
───────────────────────────────────────────────────────────────
AeroEngine → RenderContext ─┬→ SceneRenderer (纯渲染执行)
                             ├→ CommandBus (命令队列 + 日志)
                             └→ StateSnapshot (可查询的引擎状态)

目标：引擎可通过结构化命令被外部控制
关键交付物：命令系统设计文档、至少 3 个只读命令、命令权限分级

═══════════════════════════════════════════════════════════════

阶段 3-4 — AI 接入 + 语义层
───────────────────────────────────────────────────────────────
AeroEngine → RenderContext → SceneRenderer
              ├── CommandBus ──→ LLM Tool Schema (外部 LLM)
              ├── SemanticContext
              │   ├── StructuralDigest (空间统计、材质分类)
              │   ├── SceneMetadata  (作者标注通道)
              │   └── VisualQuery    (离屏截图 → 多模态 LLM)
              └── ConstraintSystem  (操作安全检查)

目标：AI 能理解场景、安全操作引擎
关键交付物：至少 5 类只读 + 3 类编辑任务稳定可演示

═══════════════════════════════════════════════════════════════

阶段 5-7 — AI-Native
───────────────────────────────────────────────────────────────
AeroEngine → RenderContext
              ├── [语义层] → Embedding 模型 (预训练 ONNX)
              ├── [约束层] → 确定性的规则引擎
              ├── [分析层] → 传统 CV 算法 (histogram, K-means)
              ├── [规划层] → LLM / 本地模型 (异步)
              └── [执行层] → 安全的命令执行 + 回滚

目标：异构 AI 组件协同，引擎提供多层次表征
关键交付物：本地推理原型、混合路由策略、AI-Native 方法论总结
```

## 3. RenderContext 设计

### 3.1 定位

RenderContext 是**渲染能力的统一门面**。它不增加运行时开销（编译期内联、值类型），
只重新组织代码归属：

- **SceneRenderer**：纯渲染执行，不持有场景引用，不参与协调
- **RenderContext**：场景绑定与切换、热重载编排、状态查询
- **AeroEngine**：生命周期和主循环，通过 RenderContext 操作渲染

### 3.2 为什么引入

1. **统一能力面**：人类（ImGui）和 AI（Tool Call）面对同一套接口
2. **命令系统种子**：阶段 2 的 `EngineCommandBus` 直接建立在 RenderContext 上
3. **解耦场景数据与渲染执行**：SceneRenderer 通过 `const GpuScene*` 借用数据，
   不持有所有权

### 3.3 非侵入性

```cpp
class RenderContext {
    SceneRenderer _renderer;  // 值类型，无堆分配
public:
    void draw(VkCommandBuffer cmd, ...) {
        _renderer.draw(cmd, ...);  // 编译期内联，零开销
    }
};
```

## 4. 语义层设计

### 4.1 核心原则

- **引擎不做"理解"，引擎做"表征"**：引擎的职责是把 15 万顶点压缩成 AI 能消费的形式；
  AI 的职责是在压缩后的表征上推理
- **分层延迟计算**：便宜的推导先做（<1ms），贵的 LLM 查询按需（缓存在 scene hash 上）
- **非侵入性**：没有 metadata 引擎照常渲染，有 metadata 语义层才生效

### 4.2 语义的三个来源

```
Layer 0: Raw Data (始终可用，零成本)
─────────────────────────────────────
vertices, indices, materials, textures, AABBs

Layer 1: Structural Digest (引擎侧计算，确定性)
─────────────────────────────────────────────────
├── 空间统计：AABB 聚类、密度分布、主轴方向
├── 材质分类：PBR 参数 → roughness/metallic 分组
├── 几何特征：长宽比、位置分布、重复模式检测
└── 结构关系：包含、相邻、遮挡关系

Layer 2: Authored Metadata (可选，人工/工具提供)
──────────────────────────────────────────────────
├── glTF extras → object tags & groups
├── 外部 metadata.json → 场景描述、标签
└── 命名约定解析 ("Wall_North_01" → wall, north)

Layer 3: AI-Visual Digest (按需，昂贵但最深)
───────────────────────────────────────────────
├── 离屏截图 → 多模态 LLM 理解
├── Object ID map → 像素级归属
└── Before/After diff → 操作影响可视化
```

### 4.3 缓存策略

```cpp
struct CachedDigest {
    uint64_t sceneHash;       // 场景内容哈希
    DigestLevel level;
    std::string digest;       // 自然语言或 JSON
    uint64_t timestamp;
};
// sceneHash 不变 → 直接返回缓存，避免重复 LLM 调用
```

## 5. AI 组件矩阵（阶段 5-7）

不是一个大 LLM 控制一切，而是一组专业化组件：

| 组件 | 技术 | 延迟 | 职责 |
|------|------|------|------|
| 意图理解 | LLM (外部 API) | 100ms+ | 自然语言 → 结构化意图 |
| 场景分析 | 多模态 LLM | 500ms+ | 理解截图/渲染结果 |
| 语义嵌入 | 预训练 ONNX 编码器 | 10-50ms | 材质/对象 → 向量搜索 |
| 程序分析 | 静态分析 + 规则 | <1ms | Shader 复杂度、draw call 分析 |
| 约束验证 | 确定性的规则引擎 | <1ms | 操作前安全检查 |
| 模式检测 | 传统统计算法 | <1ms | 性能异常、帧时间趋势 |
| 视觉特征 | 传统 CV (histogram/K-means) | <0.1ms | 光照分布、色调聚类 |

**关键：大部分"智能"不需要深度学习。传统 CV 算法 + 规则引擎覆盖了大量场景分析需求。**

## 6. 共创模式 (Co-Creation)

### 6.1 定义

共创不是"LLM 命令 → 引擎执行"的单向管道，而是**三方面对一个共享表征**：

```
        用户
         │
    ┌────┴────┐
    │         │
   LLM ─── 共享表征 ─── 引擎
    │         │           │
    │    ├─ 场景摘要      ├─ 渲染
    │    ├─ 材质嵌入      ├─ 预览
    │    ├─ 约束状态      ├─ 验证
    │    └─ 操作 diff     └─ 执行
    │
    └── 引擎持续产出"LLM 可消费的反馈"
        LLM 持续产出"引擎可执行的计划"
        用户始终在循环中
```

### 6.2 解决了什么

- **幻觉问题**：LLM 不猜测引擎状态，直接读取结构化表征
- **上下文漂移**：共享表征是唯一真相源 (single source of truth)
- **失败恢复**：操作前约束检查 → 结构化错误反馈 → LLM 调整计划

## 7. 设计决策记录

| 决策 | 结论 | 理由 |
|------|------|------|
| RenderContext 何时引入 | 阶段 1 收尾（当前） | 代码改动小，为阶段 2 打基础，不引入运行时开销 |
| 语义层放引擎侧还是 AI 侧 | 引擎侧提供表征，AI 侧做推理 | 引擎擅长压缩和组织数据，AI 擅长理解和推理 |
| LLM 的角色 | 意图理解 + 高层规划，不参与精确状态管理 | LLM 不适合确定性逻辑和数值分析 |
| 语义来源优先级 | 先做 Layer 1（结构推导），再做 Layer 2-3 | Layer 1 是纯数学，零依赖，可立刻开始 |
| 性能策略 | AI 线程与渲染线程完全异步 | LLM 延迟是帧时间的 100+ 倍，同步不可行 |
| 模型部署策略 | 优先用预训练 ONNX 模型，不做训练 | 降低 AI 专业门槛，专注于引擎侧能力 |

## 8. 开发者须知

作为个人项目开发者，不需要成为 AI 专家。核心竞争力在**引擎侧**：

1. **提供好的表征** — 结构化场景状态，任何 AI 都能消费
2. **提供安全边界** — 约束系统，让 AI 操作不会破坏引擎状态
3. **提供反馈回路** — 操作前/后 diff，让 AI 能自我纠正

AI 侧的模型直接使用**预训练成品**（ONNX Runtime + 开源编码器 + 外部 LLM API）。
不训练、不微调、不做模型优化——这些不是引擎开发者的工作。
